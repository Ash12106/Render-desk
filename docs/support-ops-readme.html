01 / Scope

Product scope

Support Ops Desk is a full-stack service ticket management system with separate customer and staff experiences, administrator task management, assignment groups, staff availability, ticket activity tracking, audit logs, attachments, and operational reporting.

Customer viewRegister, sign in, create tickets, follow status, receive notification records, add comments, and manage profile information.
Staff workspaceWork assigned tickets, update lifecycle and activity state, add comments, download attachments, and publish availability.
Administrator workspaceManage users, roles, branches, teams, availability-aware assignment, bulk assignment, and reporting.
Recovery and auditArchive deleted tickets into deleted_tickets, preserve history, and allow administrator restore.
02 / Capabilities

Core capabilities

  • Lifecycle states: Open, In Progress, Resolved, and Closed.
  • Activity states: Unread, Read, Awaiting customer response, and Awaiting technician response.
  • Operational fields for priority, type, contract, ticket form, impact, product family, due date, assignment group, and attachments.
  • Audit records for creation, lifecycle changes, priority changes, activity changes, comments, deletion, and restoration.
  • URL-driven search, filters, pagination, sorting, and table/Kanban view state.
  • Optimistic UI with rollback for comments, lifecycle changes, activity state, and staff availability.
  • Swagger UI at /api-docs and MongoDB readiness at /api/health/db.
03 / Architecture

Architecture

  • src/: Vite React frontend with React Router, TanStack Query, Tailwind CSS, Recharts, and Motion.
  • server/: Express API, Mongoose schemas, authentication middleware, validation, migrations, notifications, and tests.
  • server/index.ts: development server entry point and production API/static-file server.
  • server/mongo.ts: MongoDB connection, schemas, migrations, and transactional data operations.
  • dist/: generated production frontend and bundled server output. Do not edit manually.

05 / Setup

Prerequisites and environment

  • Node.js 22 or newer recommended. The Docker image uses Node.js 24.
  • npm and MongoDB 7 or newer, local or hosted.
  • Docker Desktop with Compose v2 for the container workflow.

Copy .env.example to .env and configure:

MONGO_URI=mongodb://localhost:27017/support-ops
PORT=3000
CORS_ORIGIN=http://localhost:3000
ADMIN_PASSWORD=change-this-before-sharing
GOOGLE_CLIENT_ID=
VITE_GOOGLE_CLIENT_ID=

MONGO_URI is preferred; MONGODB_URI remains supported for compatibility. Never commit .env.

06 / Development

Local development

npm install
cp .env.example .env
npm run dev

The app opens at http://localhost:3000. Staff and administrator login is at /login; customer login and registration is at /customer/login.

The server listens on 0.0.0.0 for LAN use. Use a host IP such as http://192.168.1.25:3000/login from another device on the same network.

Seed data

npm run seed

The seed script adds up to 12 customers and 50 tickets without deleting existing data. Startup migrations create or update the default administrator using ADMIN_PASSWORD.

07 / Delivery

Docker deployment

docker compose up --build -d
docker compose ps
curl http://localhost:3000/api/health/db

The Compose stack contains the compiled app, MongoDB 7 configured as a single-node replica set, a one-shot initializer, and the persistent mongo_data volume.

Use docker compose down to stop without deleting data. Use docker compose down -v only when intentionally resetting the database.

Expected result: the app container is running, MongoDB reports healthy, and the health endpoint returns HTTP 200 with a connected database response.

The current local verification passed TypeScript, ESLint, Prettier, 31 Vitest tests, and the production build. The Docker path also built and started successfully.

Vite may report that the main browser bundle exceeds 500 kB. This is a performance warning, not a failed build. Future optimization can use route-level dynamic imports and Rollup chunk configuration.

09 / API

API surface

Health and documentation

  • GET /api/health/db: MongoDB readiness and ping status.
  • GET /api-docs: Swagger UI.

Authentication

  • POST /api/auth/login: staff/admin login.
  • POST /api/customer-auth/register: customer registration.
  • POST /api/auth/google: Google sign-in when configured.

Tickets

  • GET /api/tickets, GET /api/tickets/stats, and GET /api/tickets/:id.
  • POST /api/tickets, PUT /api/tickets/:id, and DELETE /api/tickets/:id.
  • Comment, activity-status, assignment, bulk-status, archive, and restore routes.

Protected routes currently use Authorization: Bearer <user-id> in the development authentication model.

10 / Handoff

Operational and security notes

  • Helmet, rate limiting, Zod validation, authentication middleware, archived deletion, and transactional writes are enabled.
  • Set an explicit, restricted CORS_ORIGIN in production.
  • The current browser-stored user ID bearer-token model is intended for development. Use HTTPS and secure server-managed sessions or signed short-lived tokens before public exposure.
  • Run npm audit --omit=dev before deployment and review the currently documented moderate advisory inherited through Express 4.
  • Keep startup, migration, seed, notification, and error logs, but replace them with structured, redacted logging for production.
